## Project layout

- The app lives at the repository root (no subfolder, no `lovable.toml` run overrides) — the publish build installs from the root `package.json` and ignores run overrides.
- Merchant private screens live under the authenticated layout; authenticated server functions and owner-scoped RLS enforce access independently of the UI.
- Merchant summaries derive from persisted orders and order items, using Nairobi calendar periods and confirmed product revenue; no seed data or fallback business totals.
- Merchant preparation uses a narrowly scoped database function; merchants cannot change payment confirmations or delivery status directly.
- Merchant order responses are server-authoritative: a database trigger sets the response deadline from the policy table, only the respond/expire database functions change response fields, and expiry never accepts or declines for the merchant.
- The order assistant keeps rules-first intent parsing in a pure module (tested) and only calls the AI for unclear speech; AI-interpreted accept/decline always asks the merchant to confirm first.
- Product images go through the photo studio records: originals and AI versions are separate rows with origin labels, only the approval database function publishes a studio image, and a trigger derives the product's image label so it can't be typed in.
- Shopper home screens (Discover, Reels) use the light `.landing` token scope and the shared ShopBottomNav; other marketplace pages keep the dark Shell until redesigned, so restyling stays per-screen.
- Checkout is one standalone page (no bottom nav) under the `.landing` scope; its rules live in a pure tested module, `/payment` redirects to it, and the order server function requires a name and Kenyan mobile so riders and shops can reach the shopper.
- The Beez brand mark is the checked-in file `src/assets/beez-mark.png`, imported directly; never reference it through a platform asset pointer, because those pointers resolve to URLs that 404 in this project.
- Merchant and rider dashboards guard themselves in `beforeLoad` with a fresh role check (signed-out → sign-in with `next`, no workspace → that onboarding); every nav links straight to the dashboard so links never depend on roles still loading.
- Marketing info pages (Features, How it works, FAQ) are separate routes sharing the InfoPage layout and the SiteMenu side drawer; add new info pages there so the drawer and header stay consistent.
- The shopper voice assistant mirrors the order assistant: rules-first list parsing in a pure tested module, AI only for unclear or unmatched requests, products picked only from the live catalogue, and nothing enters the cart until the shopper taps add.
- Shopper M-Pesa uses Daraja STK push: rules in the pure tested `mpesa-stk` module, only `service_record_mpesa_result` (server-only) marks an order paid, and the status check queries Safaricom directly so payments resolve even if callbacks never arrive.
- Orders and order items are inserted only by the `createCustomerOrder` server function with the admin client; shoppers have no direct insert, so prices and payment status can't be self-set.
- Shoppers check out as guests: `startGuestSession` (IP rate-limited) creates a guest-flagged account (app_metadata.guest) and a one-time sign-in code, so RLS by customer_id still works; role/dashboard checks use `getAccountSession`, which treats guests as signed out.
- M-Pesa B2C (refunds, rider payouts) is sent only from server functions via `mpesa.server.ts`, with Safaricom results posted to neutral `/api/public/payouts/*/{type}/{key}` routes; Safaricom rejects callback URLs containing "mpesa", and edge functions aren't used for payments.
- The merchant Analytics tab renders only figures from the pure tested `merchant-analytics` module (paid, not-cancelled product revenue; comparisons against the same point of the previous period), so sales rules live in one place.
- Reel videos (product clips and shop intros) reach customers only after admin approval; review/checklist rules live in the pure tested `reel-video` module and reel ordering in `reel-feed`, so both screens and the feed share one rule set.
- Merchant video review texts are sent only by the review server functions after the database review succeeds; SMS failures never undo or block a review.
- Live tracking rules (ping throttle, 45 m/s jump filter, stages, route refresh, ETA, marker easing) live in the pure tested `live-tracking` module; riders send locations only through `rider_location_ping`, which re-checks them server-side, and the customer map keeps one `LiveTrackingMap` interface so the map provider can be swapped without touching tracking logic.
- Rider handovers (pickup, drop-off) complete only through `verifyHandover` after a signed QR or 4-digit code check; offer countdown, next-step, wallet-ledger and today-timeline rules live in the pure tested `rider-jobs` module and offline-scan rules in `handover-queue`, so the rider screens hold no business rules.
